# 阶段 2 对照实验：字符集 / NUL / 跨块（优化前基线）

日期：2026-09-08　状态：**完成，第一刀已锁定**
被测 JDK：`D:\kona\TencentKona-25\build\release\images\jdk`（25.0.4-internal，无本地改动）
机器：i9-12900HX / 24 线程 / Windows

## 1. 这轮要解决什么问题

v2 基线观察到"Unicode 读吞吐只有 StringList 一半"，但**无法归因到字符集**：
UnicodeList 是 64 个元素约 2 003 B，StringList 是 128 个元素约 1 596 B——
元素数和字节量两个变量混在一起。阶段 0 用 K 扫描证明了 Unicode 类载荷是
per-object 主导，但没回答"贵在哪"。

本轮用**单变量对照**把结论钉死。

## 2. 对照设计

载荷已由 `PayloadSizeProbe` 校验大小与往返语义（含 NUL）：

| 组 | 载荷 | 每串 | 序列化大小 | 隔离的变量 |
|---|---|---|---:|---|
| 等字节 | `Ascii96` | 96 个 ASCII | **6 394 B** | — |
| 等字节 | `Cjk32` | 32 个汉字 | **6 394 B** | 字符集 |
| 等字节 | `Emoji16` | 16 个 emoji(增补平面) | **6 394 B** | 字符集 |
| 等字符 | `Ascii32` | 32 个 ASCII | 2 298 B | 编码宽度（字节量 2.78×） |
| NUL | `Nul32` | 32 字符含 U+0000 | 2 362 B | modified UTF-8 的 C0 80 规则 |
| 跨块 | `Ascii1020` | 1020 字符 | 1 027 B | 块内 |
| 跨块 | `Ascii1030` | 1030 字符 | 1 037 B | 越过 1024 边界 |
| 跨块 | `Ascii4096` | 4096 字符 | 4 103 B | 多次越界 |
| 跨块 | `Cjk350` | 350 汉字 | 1 057 B | 中文越界 |

两点设计要点：

1. **三组等字节载荷精确同为 6 394 B**（CJK 序号特意改用汉字，避免混入
   1 字节 ASCII 数字导致失准）——只有字符集不同，是金标准对照；
2. `Nul32` 的 2 362 B 证明 `U+0000` 确实按 `C0 80` 占 **2 字节**
   （若误用标准 UTF-8 应为 1 字节），这条同时是后续优化的**正确性哨兵**。

## 3. 结果（误差 1.3–5.3%，判据可靠）

### 3.1 等字节对照（6 394 B，只有字符集不同）

| 侧 | Ascii96 | Cjk32 | Emoji16 | 结论 |
|---|---:|---:|---:|---|
| 写 | **210 055** ops/s | 112 001（慢 **1.88×**） | 111 455（慢 **1.88×**） | 字符集影响巨大 |
| 读 | **93 361** ops/s | 76 651（慢 1.22×） | 76 431（慢 1.22×） | 影响中等 |
| 写 B/op | 18 584 | 18 584 | 18 584 | **三者完全相同** |
| 读 B/op | 20 668 | 32 748（+58%） | 31 956（+55%） | 读侧分配随字符集涨 |

**关键推论**：

- 写侧 B/op 三组**完全相同**（18 584 B）⇒ 写侧差距**不是分配问题，是纯 CPU
  编码成本**，搬同样多字节中文/emoji 要花近两倍时间；
- `Cjk32` 与 `Emoji16` 数值几乎一致（写 112 001 vs 111 455、读 76 651 vs
  76 431）⇒ **成本由 UTF 字节数决定，与字符数/是否代理对无关**；
- 读侧 B/op 高 55–58%，说明读侧存在随字符集增长的临时分配（`cbuf` 等）。

### 3.2 等字符数对照（每串 32 char）

| 侧 | Ascii32 | Cjk32 | 慢 | 字节量倍数 |
|---|---:|---:|---:|---:|
| 写 | 263 369 | 112 001 | 2.35× | 2.78× |
| 读 | 122 170 | 76 651 | 1.59× | 2.78× |

写侧耗时增长（2.35×）与字节量增长（2.78×）接近线性 ⇒ 写侧成本基本由
**待编码字节数**决定。

### 3.3 跨块对照（负面结论）

| 侧 | 块内 1020 | 跨块 1030 | 耗时比 |
|---|---:|---:|---:|
| 读 | 1 099 452 | 1 059 841 | 1.037× |
| 写 | 1 028 285 | 1 005 936 | 1.022× |

**跨过 1024 块边界只慢 2–4%**，B/op 仅差 8–16 B。
⇒ 「span 分割 / 块边界是重要成本」的假设**不成立**，阶段 3（块缓冲）
优先级下调。

## 4. stack 热点与机制（K=1，6 394 B 等字节组）

| 基准 | 顶部热点（占 RUNNABLE 样本） |
|---|---|
| writeAscii96 | `StringCoding.countNonZeroAsciiLatin1` 13.8%，`writeBytes` 7.0% |
| writeCjk32 | **`ObjectOutputStream.writeString` 24.3%**，`ModifiedUtf.utfLen` 7.4% |
| writeEmoji16 | **`ObjectOutputStream.writeString` 25.8%**，`ModifiedUtf.utfLen` 8.1% |
| readAscii96 | `readUTFSpan` 13.5% + `readUTFBody` 6.1% + `readUTF` 3.7% |
| readCjk32 | `readUTFSpan` 16.8% + `StringUTF16.putChars` 5.7% |
| readEmoji16 | `readUTFSpan` 15.7% + `StringUTF16.putChars` 4.4% |

### 机制（读 JDK 25 源码确认）

`ObjectOutputStream.writeUTFInternal`（ObjectOutputStream.java:1899）对每个字符串
**扫 3–4 遍**：

```java
int countNonZeroAscii = JLA.countNonZeroAscii(str);  // ① 向量化扫 ASCII 前缀
int utflen = utfLen(str, countNonZeroAscii);         // ② 非 ASCII 时逐字符算长度 ← 慢
writeBytes(str, countNonZeroAscii);                  // ③ bulk 写 ASCII 部分
if (countNonZeroAscii != strlen)
    writeMoreUTF(str, countNonZeroAscii);            // ④ 逐字符编码多字节 ← 慢
```

- **纯 ASCII**：`countNonZeroAscii == strlen`，② 走快路径、④ 整个跳过 ⇒ 只有 ①③；
- **中文/emoji**：`countNonZeroAscii` 接近 0，②④ 都得逐字符走完整循环。

这就是写侧 1.88× 差距的来源：ASCII 有 bulk 快速路径，多字节字符没有。

## 5. 结论：第一刀落在哪

**第一刀 = `ObjectOutputStream$BlockDataOutputStream.writeUTFInternal` 的
非 ASCII 路径**（② `utfLen` 与 ④ `writeMoreUTF` 两处逐字符循环）。

支持证据（三条互相独立）：

1. 等字节下写侧慢 1.88×，且 B/op 完全相同 ⇒ 纯 CPU 编码问题；
2. stack 命中 `writeString` 24–26% + `utfLen` 7–8%；
3. 源码层面确认存在可消除的重复扫描（② 与 ④ 都是逐字符循环）。

**第二优先级**：读侧 `readUTFSpan`（13–17%），等字节下慢 1.22×，
B/op 高 55–58%（有临时分配可挖），但预期收益小于写侧。

**不做**：阶段 3 块缓冲/块模式切换——跨块实验显示只慢 2–4%，证据不足。
（阶段 0 看到的 `setBlockDataMode` 12.8% 属于写 UnicodeList 时的模式切换，
与本轮块边界成本是两回事，暂不合并处理。）

## 6. 改动约束（必须守住）

- `U+0000` 必须继续编码为 `C0 80`（`Nul32` 载荷 + `verifyNulList` 是哨兵）；
- 不得改用标准 UTF-8；
- 超长串（>0xFFFF 字节）走 `TC_LONGSTRING` 分支的行为不能变；
- 往返语义、损坏流、旧流兼容性由 jtreg 子集保证。

## 7. 验收方式（基线已备好）

改完后**紧邻重跑同一条命令**对比本文件数据：

```
java -jar jmh/target/serialization-bench.jar "StringCharsetBench" \
  -f 2 -wi 3 -i 5 -w 1s -r 1s -foe true -prof gc -rf csv
```

主判据：`writeCjk32` / `writeEmoji16` 的 ops/s 是否向 `writeAscii96`
（210 055）靠近；同时 `writeAscii96` 不得回退、B/op 不得上升。
