## 3. stack 时间热点（K=128，per-object 视角，CPU 采样）

读侧各载荷第一热点一致为 `ObjectInputStream$PeekInputStream.readFully`
（读/搬底层字节，占 RUNNABLE 样本 ~21–26%），属数据搬运；
真正与序列化算法相关的热点如下：

| 载荷 | 热点方法（占 RUNNABLE 样本） | 含义 |
|---|---|---|
| readKUnicodeList | `readUTFSpan` 11.1% + `readUTFBody` 3.3% + `StringBuilder.toString` 3.1% | modified UTF-8 解码 + 字符串装配 |
| readKCustomer | `FieldReflector.setObjFieldValues` 4.2% + `setPrimFieldValues` 4.0% | 反射写字段（非 FieldValues 构造） |
| readKOrder | `setObjFieldValues` 5.2% + `readUTF` 2.8% | 同上 |
| readKPoint | `readHandle` 3.3% + canonical 构造器相关 2.3% | record 句柄/装配路径 |
| writeKUnicodeList | `setBlockDataMode` **12.8%** + `writeMoreUTF` 12.3% + `HandleTable.lookup` 6.6% + `countNonZeroAscii` 5.7% | UTF-8 编码 + **块模式切换** + 句柄查表 |

`FieldValues.<init>` 在所有读侧采样中占比 ≈1.2%，不是 CPU 时间热点。

## 4. 决策（对应 optimization-plan 3.3）

1. **小对象（Customer/Point/record）读写：K=1 时 ~94–98% 是 per-stream 固定成本**，
   K=128 时单对象分配已压到 109–286 B（接近对象本身+字符串下限）。
   ⇒ 按 plan 3.3：**先隔离/优化基准包装层，不立即修改 FieldValues**。
   在这些载荷上池化 FieldValues 的收益空间很小（每对象只剩几百字节可省，
   且 FieldValues 构造不是 CPU 热点）。

2. **UnicodeList 读写：objects/s 随 K 基本持平（1.09×/0.84×），单对象分配在
   K=128 仍高达 5.5–13.7 KB ⇒ per-object 成本主导**；stack 在读写两侧都命中
   modified UTF-8 编解码路径（readUTFSpan/readUTFBody、writeMoreUTF/
   countNonZeroAscii）。
   ⇒ **第一刀落在字符串编解码（plan 阶段 2）**：先按 5.1/5.2 做受控拆分实验
   （ASCII vs 中文 vs emoji vs NUL、跨 1 KiB 边界），再决定写侧快速路径与读侧
   解码改造。

3. **Order（嵌套对象图）读：固定成本 68% + per-object 4.9 µs/2.9 KB 均有分量**。
   若要做 FieldValues/临时数组归因，应选这类中大型嵌套读载荷做受控实验
   （在 Order 上做，而不是 Customer 上做）。

4. **写 Unicode 的 `setBlockDataMode` 12.8%**：提示字符串批量写入时 block data
   模式切换成本不低，与 plan 阶段 3（块缓冲/块头）相关；作为阶段 2 之后的
   第二候选，不直接动 `MAX_BLOCK_SIZE`。

5. **Analytics（大数组）**：per-byte/GC 主导、吞吐噪声 ±38%+，非序列化算法
   热点；本轮不动，后续只以 B/op 判断趋势。

## 5. 给「2.2 用 CodeBuddy 优化」的入口建议

- **当前最合理的刀口顺序**：阶段 2（字符串编解码，UnicodeList 载荷有
  per-object 主导 + stack 双重证据）＞ 阶段 1 缩小到 Order 类嵌套读的
  FieldValues 受控归因 ＞ 阶段 3 的 block-data 模式切换实验。
- **动刀前的验收前置**：阶段 2 的对照载荷（纯 ASCII/中文/emoji/NUL/超长/
  跨块）需要先补齐并确认能在 B/op 与吞吐上分辨信号（plan 5.2）。
- **基准口径**：对小对象，建议 A/B 以「复用流或 K≥16 批」口径为主，
  one-shot 数值会被固定成本淹没，不适合观察 JDK 内部改动。
- **数据边界**：吞吐数值只做方向性参考；任何优化结论必须同时看
  B/op（±0.1 B 精确）与 GC 时间，且满足 plan 9 的误差规则。
