## 1. 目标与约束

我的目标是在不改变 Java 序列化协议、对象语义和兼容性的前提下，降低默认
`ObjectOutputStream`/`ObjectInputStream` 路径的时间和分配成本。

约束条件如下：

- 每个优化点必须通过相关 jtreg、往返语义和旧流兼容性验证；
- 不把 JMH 包装层成本误写成纯 JDK 内部算法成本；
- 不依赖 `java.base` 之外的 JDK 私有接口；
- 自定义 `readObject`、`readFields`、`GetField`、异常和 failure atomicity 语义不能改变。

## 2. 基线能说明了什么？

当前 JMH 的一次操作是内存字节数组场景下的端到端操作：

- 写侧：创建 `ByteArrayOutputStream` 和 `ObjectOutputStream`，写入对象，关闭/flush，调用 `toByteArray()`；
- 读侧：创建 `ByteArrayInputStream` 和 `ObjectInputStream`，调用 `readObject()`；
- 复用流：同一个输出流每轮 `reset()`、写入、flush，再清空底层缓冲。

这套基线适合做同机、同 JDK、同命令的 A/B 比较，但不能直接代表剥离流生命周期后的纯内部算法耗时。

数据中的主要信号如下表：

| 观察 | 基线证据 | 初步假设 |
|---|---|:--|
| 读侧分配明显高于写侧 | `readCustomer` 5,000 B/op vs `writeCustomer` 2,904 B/op；`readOrder` 11,112 B/op vs `writeOrder` 8,240 B/op | 可能有 `FieldValues`、字段数组和流级临时对象共同参与 |
| 小对象结果容易被固定成本稀释 | Customer 只有 247 B，但每次读分配约 5 KB | 需要分离 per-stream 与 per-object 成本，不能直接假定 FieldValues 是主因 |
| 大数组噪声很高 | `readAnalytics` ±38.5%，`writeAnalytics` ±40.0% | 先看分配和 GC，再判断数组读写路径 |
| Unicode 读侧明显慢 | UnicodeList 读吞吐约为 ASCII 列表的一半 | modified UTF-8 解码值得单独测量，但两个现有载荷大小和元素数不同，不能直接归因 |
| record 读侧可能有固定成本 | `readPoint` 512.8 K ops/s、3,437 B/op | 需要和同字段普通 Serializable 类对照后再决定是否改 record 路径 |
| 复用流显著减少分配 | Customer 2,904 B/op 降至 288 B/op | 这是流生命周期差异证据，不等于 JDK 内部热点 |

## 3. 阶段 0：提高判别力

### 3.1 放大性基准

增加一组 `K` 扫描基准，`K = 1, 16, 128`：

- 写侧：一个 `ObjectOutputStream` 连续写入同一载荷 K 次，最后 flush 并消费结果；
- 读侧：一个 `ObjectInputStream` 连续读取 K 个对象；
- 同时报告总 ops/s以及归一化后的 objects/s 和 B/object。

随着 K 增大，流创建、stream header、关闭和 `toByteArray()` 等固定成本会被摊薄。
比较 K=1 与 K=128 的斜率即可判断优化信号主要来自 per-stream 还是 per-object。
该基准仍保留现有 one-shot 基准。

### 3.2 时间热点采样

在归因阶段增加短配置的 `-prof stack` 运行，用于确认时间热点；stack 结果只用于
定位，不与正式吞吐分数混合。若 Windows 环境或当前 JMH 构建无法提供 stack
profiler，则记录失败原因，改用受控拆分基准和 `-prof gc` 的分配/GC 数据。

### 3.3 阶段 0 的决策规则

- 若 K 扫描显示固定流成本占主导：先优化或隔离基准包装层，不立即修改 `FieldValues`；
- 若 per-object 成本随 K 增长仍占主导：进入阶段 1 的读侧临时对象归因；
- 任何候选点都必须同时观察吞吐、B/op 和 GC 时间，不能只以 B/op 作为“加速”证据。

## 4. 阶段 1：读侧临时对象归因与优化

先在 `ObjectInputStream.readSerialData` 和 `FieldValues` 周围做受控归因，确认每种
载荷实际创建了哪些对象和数组，再决定是否按嵌套深度复用临时数组。

只有在阶段 0 证明 per-object 分配是主要成本时，才实施池化：

- 仅限没有自定义 `readObject`、`readFields` 或 `GetField` 暴露风险的内部路径；
- 不能回收可能被用户代码继续持有的 `objValues`、`objHandles`；
- 保留 failure atomicity、异常退出和自定义反序列化的原有生命周期。

验收：读侧 B/op 下降，同时 objects/s 不回退；所有相关 jtreg 和兼容性测试通过。

## 5. 阶段 2：字符串编码和解码

### 5.1 写侧 ASCII 快速路径

在 `writeUTFInternal` 上先用匹配长度、字符串数量、NUL 字符的控制实验确认收益，
再优化短纯 ASCII 路径。必须保持 modified UTF-8 规则，不能用普通 UTF-8 替换。

### 5.2 读侧 UTF-8 解码路径

为 ASCII、中文、emoji、NUL、跨 1 KiB block 边界的字符串增加对照载荷，定位
`readUTFBody` 的 StringBuilder/cbuf 和 span 处理成本。只有在 stack 或 K 扫描显示
解码占据可观时间后，才优化读侧；否则保留为已验证但暂不实施的假设。

验收：写侧和读侧对应字符串基准改善，Unicode、NUL、超长字符串、损坏流和
兼容性测试不回归。

## 6. 阶段 3：块缓冲实验，不直接把 1 KiB 改成 8 KiB

当前 `MAX_BLOCK_SIZE` 同时影响内部缓冲和分段逻辑。直接扩大初始缓冲会让每次
新建小流增加约数 KiB 固定分配，可能损害 Customer、Point 等高频小载荷。

我的实验顺序：

1. 保持小载荷初始缓冲为 1 KiB；
2. 只在大数组或连续 primitive 批量路径需要时按需扩容，或使用独立 bulk buffer；
3. 比较 1 KiB、4 KiB、8 KiB 对 Analytics、StringList、UnicodeList 以及 Customer/Point 的双向影响；
4. 把小载荷回退和大载荷收益分开报告，不能用平均分掩盖 trade-off。

块边界可能影响 `available()`、`OptionalDataException`、自定义 `readObject` 和异常流处理。当前 checkout 没有独立的 `test/jdk/java/io/ObjectOutputStream` 目录时，应从现有 Serializable block-data 用例中筛选并补充专门的边界测试；若后续建立该目录，则将其加入测试入口。不能只依赖当前 160 个顶层条目。

## 7. 阶段 4：record 路径

新增与 `Point` 字段数量和类型完全一致的普通 Serializable 类作为对照。只有在对照和 stack 结果确认 canonical 构造器装配是固定热点后，才优化 `ObjectStreamClass`的 record 路径。不绕过 canonical 构造器、校验逻辑或异常语义。

## 8. 阶段 5：并发和复用流复核

优化完成后，用同一命令紧邻重跑 8 线程代表矩阵，判断是否明显回退。并发矩阵不计算跨时段扩展倍数。复用流继续作为独立使用模式报告，不与一次性流场景合并排名。

## 9. 分层验证流程

### 快速迭代循环

每个小改动只执行受影响的最小集合：

1. 增量重建 `java.base`；
2. 运行受影响的核心 jtreg 子集和新增兼容性测试；
3. 运行受影响的 JMH 子集、K 扫描和必要的 `-prof stack`；
4. 若功能或兼容性失败，立即回退，不进入完整性能比较。

### 验证

阶段完成或准备合并时再执行：

1. 完整 release 镜像构建；
2. 全部 160 个 jtreg 顶层条目；
3. 完整 24 基准主矩阵、GC 指标和放大性基准；
4. 基线 writer → 优化 reader、优化 writer → 基线 reader；
5. 8 线程代表矩阵回归。

高噪声方法（误差超过 15%）不得据此宣称小幅吞吐提升；需要增加迭代、重复 A/B
或只报告分配/GC 趋势。TLAB 分配下降本身不等于加速，最终必须至少有一个时间指标
改善且没有明显功能或兼容性回退。
