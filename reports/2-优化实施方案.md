# 优化实施方案（基于全部测量证据）

> 实际执行：Round1 与读侧优化均已落地并验证，过程见 [4-优化实验全记录.md](4-优化实验全记录.md)，
> 最终结论见 [5-最终交付报告.md](5-最终交付报告.md)。

被测 JDK：Kona JDK 25 release 镜像（25.0.4-internal，源码 `D:\kona\TencentKona-25`，
分支 `task2-serialization-accel`，现已含两处优化提交）

**第一处改动：`ObjectOutputStream$BlockDataOutputStream.writeUTFInternal` 的非 ASCII 路径**
（`ModifiedUtf.utfLen` + `writeMoreUTF`）。它只影响含非 ASCII 字符串的载荷，纯 ASCII 走既有快路径、不受影响，风险可控且有精确验收基线。

## 1. 证据基础（三份互相独立的测量）

| 来源 | 关键结论 |
|---|---|
| v2 基线 | Unicode 读吞吐只有 ASCII 一半（但当时无法归因） |
| 阶段 0 K 扫描 | 小对象 94–98% 是建流固定成本；UnicodeList 是 per-object 主导（1.09×/0.84×） |
| **阶段 2 等字节对照** | **写侧中文/emoji 比 ASCII 慢 1.88×，而 B/op 三组完全相同（18 584 B）** |

三条推论如下：

1. B/op 完全相同 ⇒ 差距是**纯 CPU 编码成本**，不是分配问题，只能靠改算法；
2. Cjk32 ≈ Emoji16（112 001 vs 111 455）⇒ 成本由 **UTF 字节数**决定，与字符集种类无关；
3. stack 命中 `writeString` 24–26%、`utfLen` 7–8%，且源码确认存在**可消除的重复扫描**。

## 2. P0：写侧非 ASCII 编码路径

### 2.1 位置

| 文件 | 位置 | 作用 |
|---|---|---|
| `ObjectOutputStream.java` | `writeUTFInternal`（1899） | 入口，扫 3–4 遍字符串 |
| `jdk/internal/util/ModifiedUtf.java` | `utfLen(str, countNonZeroAscii)`（62） | ② 逐字符算长度 |
| `ObjectOutputStream.java` | `writeMoreUTF`（1923） | ④ 逐字符编码多字节段 |
| `jdk/internal/util/ModifiedUtf.java` | `putChar`（40） | 单字符编码，被 ④ 调用 |

### 2.2 现状（源码）

```java
// writeUTFInternal —— 对每个字符串扫 3~4 遍
int countNonZeroAscii = JLA.countNonZeroAscii(str);   // ① 向量化扫 ASCII 前缀
int utflen = utfLen(str, countNonZeroAscii);          // ② 非 ASCII 时逐字符 ← 标量循环
writeBytes(str, countNonZeroAscii);                   // ③ bulk 写 ASCII 段
if (countNonZeroAscii != strlen)
    writeMoreUTF(str, countNonZeroAscii);             // ④ 逐字符编码 ← 标量循环
```

```java
// utfLen —— 从后往前逐个 char 判断，纯标量
public static int utfLen(String str, int countNonZeroAscii) {
    int utflen = str.length();
    for (int i = utflen - 1; i >= countNonZeroAscii; i--) {
        int c = str.charAt(i);
        if (c >= 0x80 || c == 0)
            utflen += (c >= 0x800) ? 2 : 1;
    }
    return utflen;
}
```

```java
// writeMoreUTF —— 每字符：算 csize → 查块边界 → putChar 再算一次 csize
for (int strlen = str.length(); stroff < strlen;) {
    char c = str.charAt(stroff++);
    int csize = c != 0 && c < 0x80 ? 1 : c >= 0x800 ? 3 : 2;   // 第一次判断
    if (pos + csize >= MAX_BLOCK_SIZE) { this.pos = pos; drain(); pos = 0; }
    pos = putChar(buf, pos, c);                                 // putChar 内部第二次判断
}
```

**两处浪费**：② 是纯标量逐字符循环（没有利用 `countNonZeroAscii` 已给出的信息，
也没用向量化）；④ 每个字符判断宽度两次（自己一次、`putChar` 内一次）。

### 2.3 改法（两个子项，可分别提交、分别验证）

**P0-a：`utfLen` 向量化 / 按 coder 分流**

- 对 `Latin1` 编码的 String（`isLatin1()`）：所有 char < 0x100，`c >= 0x800` 恒假，
  只需统计满足 `c >= 0x80 || c == 0` 的字节数 ⇒ 可改成批量统计循环
  （一次处理 8 字节，用 `long` 位运算批量判定），消除逐字符分支；
- 对 `UTF16` 编码的 String：按"高位字节是否为 0"分批处理，同样减少分支；
- 保持 `utfLen` 的**语义与返回值完全一致**（尤其 `c == 0` 要计为 2 字节的 `C0 80`）。

**P0-b：`writeMoreUTF` 内联 + 批量化**

- 把 `putChar` 的宽度判断内联进 `writeMoreUTF`，消除每字符的重复分支；
- 对连续同类宽度字符（例如整段 CJK 都是 3 字节）走批量写路径，
  一次搬多个字符再统一检查块边界；
- 块边界语义必须保持（`pos + csize >= MAX_BLOCK_SIZE` 时才 `drain()`）。

### 2.4 预期收益（估计）

| 载荷 | 当前 | 预期 | 说明 |
|---|---:|---|---|
| `writeCjk32` | 112 001 ops/s | 约 +5～15% | ② 7.4% + ④ ~12% 中可省部分 |
| `writeEmoji16` | 111 455 ops/s | 约 +5～15% | 同上 |
| `writeAscii96` | 210 055 ops/s | **不得回退** | 纯 ASCII 不走这两条路径 |
| 写侧 B/op | 18 584 B | **不得上升** | 本项不应引入任何新分配 |

上限参照：纯 ASCII 的 210 055 ops/s（同字节量下的"无多字节编码"基准）。

### 2.5 风险与硬约束

- `U+0000` 必须编码为 `C0 80`（2 字节），**不得**改用标准 UTF-8；
- 超长串（`utflen > 0xFFFF`）走 `TC_LONGSTRING` 分支的行为不能变；
- 块边界、`available()`、`OptionalDataException` 相关语义不变；
- `ModifiedUtf` 是 `java.base` 内部共享类，`utfLen` 若被其他调用方复用，
  改动需保证返回值语义一致（实施前先确认调用点）。

### 2.6 验收

```
java -jar jmh/target/serialization-bench.jar "StringCharsetBench" \
  -f 2 -wi 3 -i 5 -w 1s -r 1s -foe true -prof gc -rf csv
```

判据：`writeCjk32`/`writeEmoji16` ops/s 上升且误差范围不重叠；
`writeAscii96` 不回退；B/op 不上升；`Nul32` 与全部载荷往返校验通过。

## 3. P1：读侧解码 `readUTFSpan`

### 3.1 位置与现状

`ObjectInputStream.java`：`readUTFBody`（3530）与 `readUTFSpan`（3597）。
stack 显示 `readUTFSpan` 占 13–17%（三组等字节载荷）、
`StringUTF16.putChars` 占 4–6%。

等字节对照下读侧只慢 1.22×，但 **B/op 高 55–58%**（20 668 → 32 748），
说明读侧存在随字符集增长的临时分配（`readUTFBody` 的 `cbuf`、跨块时的
`StringBuilder`）。

### 3.2 改法方向（实施前需再读源码细化）

- 消除/复用 `cbuf` 临时 `char[]`（按嵌套深度复用，不做全局池化）；
- 减少 ASCII 段与多字节段之间的重复搬运；
- 直接用 `String` 构造器批量构造，避免 `StringUTF16.putChars` 的二次拷贝。

### 3.3 预期与风险

预期收益小于 P0（读侧时间差距只有 1.22×，但分配差距大）。
主判据是 **B/op 下降**，时间指标改善作为附加。风险点：异常流、
损坏流、`GetField`/自定义 `readObject` 的生命周期不能变。

## 4. 明确不做（原因如下）

| 候选 | 结论 | 原因 |
|---|---|---|
| 池化 `FieldValues` | **不做（至少不在小对象上做）** | K=128 时每对象只剩 147–286 B 分配，`FieldValues.<init>` 在 stack 中仅 1.2% |
| 改 `MAX_BLOCK_SIZE` / 块缓冲 | **暂缓** | 跨 1024 边界只慢 2–4%（读 1.037×、写 1.022×），证据不足 |
| 大数组（Analytics）路径 | **不做** | per-byte / GC 主导，吞吐噪声 ±38%+，非算法热点 |
| 一次性替换标准 UTF-8 | **禁止** | modified UTF-8 的 `C0 80` 与 6 字节增补平面规则是协议约束 |

## 5. 实施顺序

1. **P0-a**（`utfLen` 向量化）→ 重建 → 验收集（最快见效、单点最独立）
2. **P0-b**（`writeMoreUTF` 内联/批量化）→ 重建 → 验收集
3. 完整 jtreg 160 条目 + 24 基准主矩阵 + 兼容性（基线 writer→优化 reader 等）
4. **P1**（读侧）在 P0 稳定后再启动

每一步遵循：增量重建 `java.base` → 受影响 jtreg 子集 → 受影响 JMH 子集→ **失败即回退**，不带着失败进入下一步。

## 6. 回滚准则

- 任一 jtreg 条目失败 → 立即回退该提交；
- `Nul32` 或任一载荷往返校验失败 → 立即回退；
- `writeAscii96` 回退超过误差范围 → 回退；
- 吞吐提升未超出误差范围 → 不计入收益，但可保留（若分配/GC 有改善需单独说明）。
