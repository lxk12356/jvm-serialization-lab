# 第一轮实施记录（写侧 UTF 编码微优化）

日期：2026-09-08　状态：**代码已改 + 语义等价已证明；性能验证受阻**

## 1. 改动内容（2 处，均已证明语义等价）

### 1.1 `ObjectOutputStream.writeMoreUTF`（ObjectOutputStream.java:1923）

把 `ModifiedUtf.putChar` 内联展开，复用循环里已经算出的 `csize`，
消除每个字符的**重复宽度判断**（原来 `writeMoreUTF` 算一次 `csize`，
`putChar` 内部又判断一次同样的条件）。

等价性：`csize==1 ⟺ c!=0 && c<0x80`；`csize==3 ⟺ c>=0x800`，与 `putChar` 分支完全一致。

### 1.2 `ModifiedUtf.utfLen`（ModifiedUtf.java:62）

调整分支顺序，把多字节字符（`c >= 0x800`，CJK/emoji 最常见）放在首位，
使常见情形一次判断命中，利于 CPU 分支预测。语义与原实现等价。

## 2. 等价性验证（已通过）

`verify/UtfEquivalence.java`，用普通 Java 穷举对比新旧实现：

| 检查项 | 结果 |
|---|---|
| `putChar` 新旧逐字节对比（全部 65 536 个 char） | 全部一致 |
| `utfLen` 单字符串（全部 65 536 个 char） | 全部一致 |
| `utfLen` 随机混合串 20 万组（含 ASCII/NUL/2B/3B/代理对，各种 countNonZeroAscii） | 全部一致 |
| NUL 哨兵：`U+0000` 必须编码为 `C0 80`（2 字节） | 通过（实测 `C0 80`） |
| 增补平面 emoji 代理项 3 字节 | 通过 |

另：`PayloadSizeProbe` 在 patch 后的 JDK 上全部通过，**所有载荷序列化大小与基线逐字节一致**（Ascii32 2298 / Cjk32 6394 / Emoji16 6394 / Nul32 2362 …），说明新类确实生效且编码结果未变。

## 3. 性能验证尝试与失败原因

### 3.1 环境限制

当前 shell **没有 make**，WSL 被安全策略禁用，无法增量重建 `java.base`
（也就无法跑 jtreg 与"真实 JDK"下的 JMH）。

### 3.2 绕过尝试：`--patch-module`（失败）

思路：把 JDK 镜像里的 `java.base` 用 `jimage extract` 解出作为编译依赖，改动类单独编译后用 `java --patch-module java.base=...` 覆盖运行，从而免构建验证。

**编译可行**（`--module-source-path` + `module-info.java` + `--patch-module`），语义冒烟也通过，但**性能数据完全失真**：

| 基准 | 无 patch 基线 | patch 下的"未改动原始版" | 失真 |
|---|---:|---:|---:|
| writeAscii96 | 210 055 | 60 278 | −71% |
| writeCjk32 | 112 001 | 33 605 | −70% |
| readCjk32 | 76 651 | 33 182 | −57% |
| readAscii96 | 93 361 | 73 748 | −21% |

且误差从基线的 1.3~5.3% 恶化到 28%~89%。

**判断**：`--patch-module` 覆盖 `java.base` 会让这些类脱离 CDS 归档、改变加载与 JIT 行为，引入的干扰远大于改动本身的效果。
因此 A/B 结果（如 writeCjk32 +14.7%、readAscii32 −66.8%）**一律不可采信**。

结论：**该方法是不能用于性能验证的**，性能结论必须等真正的 JDK 构建。
