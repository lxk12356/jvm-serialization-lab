## 1. 为什么优化这些位置（测量驱动的动机）

### 1.1 测量链

1. **v2 基线**（24 JMH 方法）：观察到"UnicodeList 读吞吐只有 StringList 一半"，但载荷元素数/字节量不同，无法归因。
2. **阶段 0 K 扫描**（`reports/stage0-ksweep/`）：小对象（Customer/Point）每次操作94-98% 是建流固定成本 → **小对象上池化 FieldValues 是伪方向**（已证伪：K=128 时每对象只剩 147-286B 分配，`FieldValues.<init>` 在 stack 仅占 1.2%）。
3. **阶段 2 等字节对照**（`reports/stage2-strings/`）：构造三组**字节数完全相同（6394B）只有字符集不同**的载荷（Ascii96 / Cjk32 / Emoji16），结论：
   - 写侧：中文/emoji 比 ASCII 慢 **1.88×**，但 B/op 完全相同 ⇒ 纯 CPU 编码问题；
   - cjk32 ≈ emoji16 ⇒ 成本由 UTF 字节量决定，与字符集种类无关；
   - 读侧：慢 1.22×，但 B/op 高 55-58%（有分配可减）。
4. **stack 采样**（`-prof stack`）：热点定位到具体函数。

### 1.2 定位到代码（读 JDK 25 源码确认）

`ObjectOutputStream.writeUTFInternal`（1899）对每个字符串扫 3-4 遍：

```
① countNonZeroAscii  向量化扫 ASCII 前缀（快，无优化空间）
② utfLen             非 ASCII 时逐字符算长度（ModifiedUtf.utfLen，纯标量循环）
③ writeBytes         bulk 写 ASCII 段（快）
④ writeMoreUTF       逐字符编码多字节段（含 putChar 每次重复判断宽度）
```

**纯 ASCII 走 ①③（bulk）；中文/emoji ②④ 逐字符** ⇒ 这就是 1.88× 的来源。

### 1.3 优化方向池（按证据/风险排序）

| 代号 | 方向 | stack 证据 | 预期 | 状态 |
|---|---|---|---|---|
| Round1 | writeMoreUTF 内联 putChar + utfLen 分支重排 | writeString 24% | +3~5% | ✅ 已提交 `fecbb593236`，实测 +3.0% |
| **P1** | utfLen 按 coder 分流/批量 | utfLen 7-8% | +5~10% | 见 §2 |
| **P2** | writeMoreUTF 分段批量 | writeString 主体 | +3~8% | 见 §3 |
| **P3** | 读侧 readUTFSpan 解码 | 读侧 10-17% | +5~15% | 见 §4 |
| 已证伪 | FieldValues 池化 / 改块大小 / Analytics | — | — | 不做 |

## 2. Round1（已完成）：writeMoreUTF 内联 + utfLen 分支重排

- **提交**：`fecbb593236`
- **动机**：stack 显示 `writeString` 占写侧 24-26%。读源码发现 `writeMoreUTF` 每个字符先算一次 `csize`，再调 `ModifiedUtf.putChar`，而 putChar 内部**又判断一遍同样的宽度条件** ⇒ 每字符重复判断两次。utfLen 则对非 ASCII 逐字符判断。
- **改动**：
  1. `ObjectOutputStream.writeMoreUTF`：内联 putChar，按已算出的 `csize` 直接分支写字节；
  2. `ModifiedUtf.utfLen`：分支顺序调整（`c >= 0x800` 前置，CJK/emoji 最常见）。
- **语义验证**：`verify/UtfEquivalence.java` 穷举 65536 char 逐字节一致 + 20 万随机串一致；
  NUL 仍为 `C0 80`；jtreg Serializable+ObjectInputStream **154 通过**。
- **A/B 实测**（干净机器，各 12 样本）：
  - `writeCjk32` 111,213 → **114,552（+3.0%，误差 ±1.5% vs ±0.9%，不重叠 ⇒ 显著）**
  - `writeEmoji16` +2.4%（接近显著）
  - `writeAscii96` -0.5%（底线守住）；B/op 全不变
- **结论**：保留。方向正确、可证实、零风险，但幅度小（分支级微优化天花板低）。

## 3. P1（调整中）：写侧微观优化空间评估

### 3.1 初步假设与结论

初版 P1 设想"utfLen 按 String coder 分流（Latin1 批量 / UTF16 按 3 字节区间）"。查看后发现：`String.coder`/`value` 是 private，`ModifiedUtf`（jdk.internal.util）无法访问；要按 coder 分流必须给 `JavaLangAccess`（SharedSecrets）加方法，触碰 java.base 公共内部接口。而 utfLen 在 stack 只占 6.9%，优化一半仅换写侧+3~4% —— **代价与收益不匹配，放弃该路线**（避免为小收益动大接口）。

### 3.2 干净机器上的真实热点（writeCjk32，优化版 fecbb593236）

| 热点 | 占比 | 说明 |
|---|---:|---|
| `ObjectOutputStream.writeString` | 23.3% | **聚合帧**：JIT 已把 writeUTFInternal/writeMoreUTF 内联进来 |
| `ModifiedUtf.utfLen` | 6.9% | 逐字符算长度（单独可见，未完全内联） |
| `writeObject` | 5.6% | 对象分发 |
| `HandleTable.lookup/growSpine/assign` | ~4.7% | 句柄表操作（growSpine 1.4%） |
| `Arrays.fill` | 0.7% | — |

### 3.3 判断：写侧微观优化空间已逼近上限

- `writeMoreUTF` 已被 JIT 内联进 `writeString`（23.3% 是聚合值），说明编码循环本身已被充分内联优化；再抠逐字符指令的收益有限（预估每刀 +3~5% 封顶）。
- 写 CJK(114K) 与 ASCII(211K) 的 1.88× 差距，本质是**结构性成本**：多字节字符必须逐字符编码（读 char → 判宽 → 写 2~3 字节），无法像 ASCII 那样 bulk 拷贝。消除它需要向量化/分段批量编码，工程复杂且风险高。
- **结论**：剩余热点中收益明确、判据可靠的方向在**读侧**（见 §4）。

### 3.4 留档

- P1 的"utfLen 向量化"完整设计已在 `reports/2-优化实施方案.md`
  P0-a 中留档；若未来值得动 String 内部接口（如多场景共享）再评估。
- 干净机器 stack 原始文件：`reports/stage2-strings/stack-writeCjk32-clean.txt`

## 4. 下一步方向（待确认）：读侧 readUTFBody 减分配

- **动机**：等字节对照中读侧 B/op 比 ASCII 高 55~58%（readCjk32 31,944 vsreadAscii96 20,680，约 177B/串额外分配）；而 **B/op（gc.alloc.rate.norm）判据精度 ±0.1B，不受机器噪声影响** —— 这是当前唯一"机器不干净也能精确验证"的优化维度。
- **候选改动**：`ObjectInputStream.readUTFBody`（3530）的字符串构造路径。
- **前置**：需先做分配点定位（JFR 分配采样），确认 177B/串花在哪，避免盲改。

### 4.1 分配点定位结果（JFR allocation-by-site，ReadMicro 200 万次读）

| 分配点 | CJK 占比 | ASCII 占比 | 说明 |
|---|---:|---:|---|
| `StringUTF16.newBytesFor` | 56.6% | — | String 的 byte[]（CJK→UTF16） |
| `AbstractStringBuilder.<init>` | **26.7%** | **38.7%** | **每串 new StringBuilder！ASCII 也有** |
| `Arrays.copyOfRange(byte[])` | — | 39.0% | ASCII 路径的 byte[] 相关 |
| 读类描述符/OIS 构造 | ~8.5% | ~14% | 每 op 固定 |

**关键结论**：`StringBuilder` 大量分配不是 CJK 特有——**读 String 的通用路径（readUTFBody while 循环）对大量字符串每串都 `new StringBuilder` + 内部 char[]**。消除它 = 直接减掉读侧 27~39% 的分配，B/op 精确可测。

### 4.2 选定优化：复用 StringBuilder（消除每串 new）

- **位置**：`ObjectInputStream$BlockDataInputStream.readUTFBody`（3530）。
- **做法**：加一个字段级 `StringBuilder`，`getSbuf()` 懒创建 + `setLength(0)` 复用，需要时按 `utflen` 扩容；解码逻辑（while 循环/readUTFChar）不动。
- **收益预期**：readCjk32 31,944 → 约 22~24K（省 27%+ 分配）；ASCII 同样受益。
- **风险**：低。StringBuilder 只在 toString() 后释放内容（String 已拷贝，可安全覆盖）；流实例不跨线程。
- **验证**：B/op 判据 + 往返语义 + jtreg 160。

### 4.3 实现与语义验证（2026-09-09 凌晨）

- **改动**（`ObjectInputStream.java`，未提交）：
  - 字段 `private StringBuilder sbuf;`（BlockDataInputStream）；
  - `sbuf()` 方法：懒创建 + `setLength(0)` 复用；
  - `readUTFBody`：原 `new StringBuilder(capacity)` 改为 `sbuf = sbuf()` +
    按需 `ensureCapacity`（仅超长时扩容）。
- **语义验证通过**：
  - `PayloadSizeProbe` 全过（含 NUL `C0 80` 校验）；
  - 新增 `verify/RoundTripCheck.java`：跨块(1024B)/超长(>256 char)/NUL/代理对/
    随机混合 3000+ 组，原版与改动版均 PASS；
  - 完整构建与实测随后完成，结果见下文 **4.4**（readCjk32 B/op −53.3%、jtreg 160/160）。

### 4.4 实测结果与提交—— 提交 `08bc7650aa5`

**B/op（gc.alloc.rate.norm，±0.1B 精度）对比原版 round2-orig：**

| 基准 | 原版 B/op | 优化后 B/op | 下降 | 吞吐变化 |
|---|---:|---:|---:|---:|
| readCjk32 | 31,944 | **14,916** | **−53.3%** | **+6.4%（显著）** |
| readEmoji16 | 32,748 | **14,904** | **−54.5%** | **+6.5%（显著）** |
| readAscii96 | 20,680 | 13,696 | −33.8% | +3.3% |
| readAscii32 | 12,500 | 9,464 | −24.3% | +2.1% |
| write* | 不变 | 不变 | 0.00% | 写侧无回退 |

- **收益远超预期**（预期 27%，实际 CJK/emoji 减半）：StringBuilder + 其内部
  char[] 每串的分配被完全消除，同时 `toString()` 也不再叠加双份拷贝。
- **正确性**：jtreg Serializable+ObjectInputStream+ObjectStreamClass **160/160 通过**
  （首个运行 1 失败系 JTwork 目录污染——`@clean` 残留 + jtreg 未重编；
  换全新 `-w` 目录即 Passed，与改动无关）。
- **结论**：读侧减分配是比写侧微观优化更"有肉"的方向——CJK 读 B/op 减半、
  吞吐 +6.5%，B/op 判据在机器受限时依然精确可用。

## 5. 全量性能重测（2.3：优化性能 + 差异分析）

### 5.1 口径

- 被测镜像 = git HEAD（Round1 `fecbb593236` + 读侧 `08bc7650aa5` 两个 commit）。
- 跑 v2 全量 24 基准：`-f 2 -wi 4 -i 6 -w 1s -r 1s -prof gc`（实际 25m，因 jar 内
  全部基准被执行；CSV：`reports/fullbench-opt/jmh-fullbench-opt.csv`）。
- 对比基线：`baseline/jmh-baseline.csv`（9-7 21:02 采，`-f 3 -wi 5 -i 8`）。
- **判据纪律**：B/op（gc.alloc.rate.norm，±0.1B）跨时段/机器状态可比，为主判据；
  吞吐列跨时段受机器状态影响，**不构成证据**（见 5.4 铁证）。

### 5.3 差异分析

1. **降幅与载荷字符串含量严格相关**：UnicodeList(−35%) > StringList(−22%) >
   Analytics(−19%，含字符串字段) > Order/Customer(−7% 级，少量串) >
   Point(−2.5%，几乎无串) —— 收益来源明确指向 readUTFBody 的 StringBuilder 复用。
2. **无字符串载荷也降 2.5~4.6%**（Point/Derived/EnumHolder/Graph）：每次 readObject
   都要经 readClassDescriptor 读类名/字段名 UTF 串，同样走被优化的 readUTFBody。
3. **写侧 B/op 0.00%** 与两 commit 的性质一致（读侧改分配、写侧只改分支）。
4. **吞吐列不可信的铁证**：写侧分配零变化，本表写侧吞吐却 +82%~+163% —— 纯为
   9-7 基线采集时机的后台负载差。吞吐只能采信同会话紧邻 A/B（round3 的
   readCjk32 +6.4% 属此，本表吞吐一律不作证据）。

### 5.4 结论与下一步

- **已实现、可归因、已验证的收益**：
  - Round1 写侧分支微调：writeCjk32 +3.0%（紧邻 A/B 显著）；
  - 读侧 StringBuilder 复用：字符串载荷读 B/op −22~54%，全量读侧 B/op −17.1%，
    合计 −9.9%；jtreg 160/160、语义穷举等价。
- **读侧 per-string 分配已近下限**：readCjk32 14,916 vs readAscii96 13,696（优化后）
  仅差 ~9%，已接近"字符串本质表示差异"，继续抠读侧边际很小。
- **写侧 1.88×（CJK vs ASCII）为结构性多字节编码成本**：utfLen 仅 6.9% 且长度头
  要求先遍历；writeMoreUTF 已被 JIT 内联，微观已到上限。
- **进一步改进候选（证据均弱于已完成项）**：读侧 FieldReflector/字段装配（stack
  ~4-9% 但 per-op 占比小）；per-op 流创建固定成本（业务上复用流可摊薄，非算法热点）。
  建议：以 jtreg 全量回归 + 并发 t8 复测收口本阶段，若需继续则上 FieldReflector
  直写路径做受控 A/B。
