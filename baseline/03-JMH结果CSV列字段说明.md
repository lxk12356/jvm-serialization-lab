# jmh-baseline.csv 字段说明（写给新手）

这份 CSV 是 JMH 工具直接导出的机器结果，每列含义如下。
我们用的输出命令带 `-prof gc`，所以除了每个基准的“主体行”之外，
还会多出 4 行以 `:gc.*` 结尾的“附加指标行”。

## 1. 列（表头）含义

| 表头 | 含义 | 说明 |
|---|---|---|
| `Benchmark` | 基准全名 | 例如 `...SerializationBench.writeCustomer`。以 `:gc.alloc.rate` 等结尾的“同一名字”是附加指标行，不是新基准 |
| `Mode` | 测量模式 | 本项目全部为 `thrpt` = throughput，即“吞吐量”：单位时间里能完成多少次 |
| `Threads` | 线程数 | `1` 表示单线程压测 |
| `Samples` | 样本数 | 参与统计的测量迭代次数 = forks（3 个 JVM）× 每轮正式迭代数（8）= 24 |
| `Score` | 指标数值 | 具体是什么，取决于所在行的单位，见下表 |
| `Score Error (99.9%)` | 误差 | 99.9% 置信区间的半宽（±）。越大说明越不稳定（机器噪音/GC 影响）。`NaN` 表示该指标无法/无需计算误差 |
| `Unit` | 单位 | 见下表 |

## 2. 一行一个含义：主行 vs `gc.*` 附加行

### 主体行（`Unit = ops/s`）

例如：

```
...readCustomer   thrpt  1  24  138604.1  10539.3  ops/s
```

意思是：这台机器上，1 个线程每秒平均能做 **138604 次**“读一个 Customer”
操作，误差约 ±10539（约 ±7.6%）。**数字越大越快**。

### 附加行 1：`...:gc.alloc.rate`（Unit = MB/sec）

每秒分配多少兆字节内存。它表示“分配压力”：越高，越容易触发垃圾回收（GC）。
它同时受吞吐影响，所以更推荐看下一个“归一化”指标。

### 附加行 2：`...:gc.alloc.rate.norm`（Unit = B/op）

**每次操作平均分配多少字节**。这是跨前后两次优化对比最常用的指标：
它已经剔除了“跑得快慢”的影响，纯粹表示“做一次要分多少内存”，
**越小通常越好**。

### 附加行 3：`...:gc.count`（Unit = counts）

整个基准运行期间观测到的垃圾回收次数。绝对数值和运行时长强相关，
主要用于同配置前后对比（比如优化后 GC 次数是否下降）。
这一行的 `Score Error` 为 `NaN` 属正常。

### 附加行 4：`...:gc.time`（Unit = ms）

整个基准运行期间花在垃圾回收上的总毫秒数。同样用于前后对比，
越小说明 GC 停顿越少。

## 3. 三个最容易看懂的结论指标

给小白快速看表建议按这个顺序：

1. **主行 Score（ops/s）**：快不快；
2. **gc.alloc.rate.norm（B/op）**：耗不耗内存（分配越少，潜在 GC 压力越小）；
3. **Score Error**：数字可不可信（误差太大说明这次机器不够安静）。

## 4. 为什么会有 5 行“同一个基准”

因为命令行开了 `-prof gc`。它让 JMH 在每次正式迭代后顺带记录 GC 数据，
所以每个基准会导出：

1 行主体 + 4 行 gc 指标 = 5 行。

如果你只想要主体行，去掉命令里的 `-prof gc` 即可；
保留它可以让我们在优化时多一个“分配量”维度的证据。

## 5. 文件命名

- `jmh-baseline.csv`：当前完整基线 v2（24 个基准方法，含补充载荷与复用流）
  的机器结果。由于开了 `-prof gc`，每个基准占 5 行，共 120 行数据；
- `jmh-baseline-v1-10benches.csv`：早期只有 10 个基准的备份，格式相同。
- `jmh-concurrency-t8.csv`：并发梯度基线（8 线程 × 12 个代表方法，
  短配置），表头与上面相同，只是 `Threads` 列为 8。

两份文件的表头完全一致，可直接套用上面的说明。
注意：v1 与 v2 间隔数小时、机器状态不同，数值不可直接对比；
正式 A/B 必须以同一份代码、紧邻时间、同一命令行顺序执行为准。
